# new鱼排红包

适用**new.fishpi.cn**（新版）与**fishpi.cn** 聊天室的自动抢红包油猴脚本，带猜拳概率推荐，基于摸鱼派 v3 开放接口实现。作者：Mairo（v1.3.2）

## 安装

1. 浏览器安装 [Tampermonkey（油猴）](https://www.tampermonkey.net/)
2. 新建脚本，把 `fishpi-auto-redpacket.user.js` 的内容粘贴进去保存
   （或直接把 `.user.js` 文件拖进浏览器，按提示安装）
3. 打开 https://new.fishpi.cn/cr 并**登录**，页面右下角出现 🧧 悬浮按钮即启动成功

## 使用

- 点击 🧧 按钮打开面板（可拖动），或用油猴菜单
- 按钮上的**绿点** = 实时通道已连接；**橙色数字** = 今日已抢个数
- 面板四个 Tab：**设置 / 统计 / 猜拳 / 日志**
- **只有聊天室路径（`/cr`、`/chat`、`/chat-room`）会启动**：其他 fishpi 页面脚本完全静默，不发任何网络请求
- 出手节奏：红包出现后**随机 0.8~3s** 才抢，两次领取至少隔 1.5s——正常人手速，给别人留机会
- 手动抢的包（脚本在后台运行时）也会进「统计」Tab，日志标「手动抢到」；抢到后按设置自动发一句回复

## 设置项说明

| 设置 | 默认 | 说明 |
|---|---|---|
| 启用自动抢红包 | 开 | 总开关（油猴菜单也能快速切换） |
| 跳过非指定给我的专属红包 | 开 | 专属红包只抢 `recipientIds` 包含自己的 |
| 跳过自己发的红包 | 开 | |
| 允许抢心跳红包 | **关** | ⚠️ 心跳红包有**倒扣积分**风险，官方要求显式确认 `riskAccepted` |
| 猜拳红包自动出招 | 开 | ⚠️ 猜拳有输赢，输了可能倒扣积分；关闭则跳过猜拳包 |
| 出招用统计推荐 | 开 | 根据对手历史出招习惯推荐胜率最高的一招，关闭则随机出招 |
| 猜拳红包金额上限 | 2000 | 单个猜拳红包金额超过上限就跳过（0=不限） |
| 最低本金阈值 | 0 | 平分/专属红包按 `money × 个数` 计算本金 |
| 发送者黑名单 | 空 | userName 逗号分隔，如 `user1, user2` |
| 随机延迟下限 | 800ms | 红包出现后至少等这么久才出手 |
| 随机延迟上限 | 3000ms | 在下限~上限之间随机等待，**放慢手速给别人机会** |
| 领取最小间隔 | 1500ms | 两次领取之间的最小间隔（+0~400ms 抖动） |
| 每日抢包上限 | 50 | 0 = 不限 |
| 统计手动领取 | 开 | 手动点的红包也记入统计与猜拳战绩（需脚本在后台运行） |
| 抢到后自动回复 | 开 | 抢到 1.5~3s 后在聊天室发回复，10s 内连抢只回一条，猜拳输了不回 |
| 回复内容 | 谢谢老板的红包～ | 支持 `{发送者}` `{金额}` 占位符 |
| 页面内弹出提示 | 开 | 抢到时页面顶部 Toast |
| 浏览器通知 | 关 | 页面不可见时用 GM_notification 通知 |

## 猜拳概率推荐

**原理与边界**：服务端对「对方这一把出什么」是隐藏的（红包抢完才揭晓 `senderGesture`），所以做不到透视，只能做统计预测。

1. 每抢完一个猜拳包，用「我出的招 + 输赢结果」反推出对方出的招，按发送者分桶记录
2. 新猜拳包出现时计算经验概率（拉普拉斯平滑）：
   - 该发送者样本 ≥ 5 → 用他的个人分布
   - 否则全局样本 ≥ 10 → 用全局分布
   - 都没有 → 33.3%，提示无历史数据
3. 推荐能克制「他概率最高那一招」的招（等价于我方胜率最大的选择）
4. 开启「出招用统计推荐」时自动按推荐出招，否则随机

**面板「猜拳」Tab** 展示：我的战绩（胜/负/平、盈亏积分）、最近一次推荐、全局出招分布、对手出招习惯 Top 5。检测到猜拳包时日志会输出一行完整推荐，例如：

```
猜拳：沐里出招习惯 石头52% / 剪刀28% / 布20%（样本17），推荐出布
```

样本越多预测越准；对陌生人（无历史）第一把仍是等概率，这是信息论限制，不是缺陷。

## 工作原理

**实时通道三层策略**（v1.2.0，核心为根治 ticket 接口 429）：

1. **监听页面通道（主路径，零 ticket 请求）**：脚本在 `document-start` 时 hook 页面的 `WebSocket` 构造器，官方前端自己换 ticket、连接、重连、心跳——脚本只被动窃听消息，**完全不调用 ticket 接口**
2. **自有 WS 兜底**：页面通道 15s 内未就绪才启用；先抢**跨标签页单实例锁**（GM 存储，多标签页/多子域共享），任何时刻只允许一个标签页连接；页面通道恢复后自动停掉兜底
3. **限流退避**：收到 429 后等待 `max(指数退避, 限流窗口剩余)`，退避 5s 到 10min 封顶 + 抖动，**不再每秒撞接口**

**抢包流水线**：

```
监听 chat.message.created（页面通道或兜底 WS）
     → 识别 type=redPacket 的消息（消息 id 即红包 id）
     → GET  /api/v3/chat/red-packets/{id}          拉详情做规则过滤
     → POST /api/v3/chat/red-packets/{id}/claims    领取
         · 普通红包 body: {}
         · 心跳红包 body: {riskAccepted:true}
         · 猜拳红包 body: {riskAccepted:true, gesture:0-2}
         · 必带 Idempotency-Key 请求头
     → 用响应里的 amount 记账、Toast、写入统计
```

- 启动错峰：UI 启动 300ms 后拉账号信息（`/auth/refresh` + `/me`），再等 300ms 连实时通道
- **所有 v3 请求 250ms 串行节流**（对齐官方前端请求节奏）
- 请求优先走**页面原生 fetch**（`credentials:'include'`），与官方前端的 Origin/Cookie 行为完全一致——服务端会校验请求来源（`Origin/Referer` 需为 fishpi.cn 系站点，`chrome-extension://` 来源会被 403），页面 fetch 失败时自动降级为 `GM_xmlhttpRequest`
- 兜底 WS 断线重连：指数退避（5s 到 10min 封顶），每 25s 发一个 ping

## 风控与自查

- 随机延迟 + 最小间隔 + 每日上限，**不建议全部设 0**
- 收到 `429` 会按 `Retry-After`（缺失按 60s）自动暂停，重连等待取「退避」与「限流窗口」较大者，不会反复撞接口
- 主路径监听页面通道，不消耗 ticket 接口配额；兜底连接受单实例锁约束，多标签页不会叠加请求
- 若触发人机验证（geetest），需在页面上手动过一次，脚本会自动恢复
- 是否允许自动抢红包请遵守社区用户协议，风险自担

## 故障排查

| 现象 | 处理 |
|---|---|
| 无悬浮按钮 / 控制台报错 | 确认 Tampermonkey 已启用本脚本，`@match` 覆盖当前站点。**非聊天室页面本来就不显示**（白名单设计） |
| 「获取账号信息失败：请登录」 | 先在 fishpi.cn 登录，再刷新页面 |
| 日志出现「请求来源不合法」(403) | 服务端 Origin 校验失败：确认页面本身能正常刷聊天室；把浏览器控制台报错发出来排查 |
| 按钮灰点（未连接） | 前 15s：先监听页面通道，页面通道就绪后变绿；仍灰则点油猴菜单「重连实时通道」，日志会写明是频控还是其他原因 |
| 日志出现 429「操作过于频繁」 | v1.2.0 起会按限流窗口安静等待（分钟级）后自动恢复，不再每秒重试；若持续出现，关闭多个 fishpi 标签页只留一个 |
| 发现红包但一直跳过 | 日志会写明跳过原因（黑名单/阈值/上限/专属等） |
| 抢包失败提示 403/验证 | 手动完成一次人机验证后会自动恢复 |
